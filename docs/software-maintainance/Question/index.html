Semester Final​

Question 01​

(a) Compare and contrast new development and software maintenance in terms of their purpose, scope, and challenges. Why is maintenance considered an ongoing process, while new development follows a structured timeline?

Software Development

Purpose: To create a new software system from scratch to meet specific requirements.

Scope: Includes requirement analysis, system design, coding, testing, and deployment.

Challenges:

  • Understanding user requirements
  • Designing scalable architecture
  • Managing project timelines and resources
  • Handling evolving requirements during development

Software Maintenance

Purpose: To modify and improve existing software after deployment.

Scope:

  • Bug fixing
  • Performance improvements
  • Security updates
  • Adding new features or adapting to new environments

Challenges:

  • Understanding legacy code
  • Lack of documentation
  • Risk of introducing new bugs
  • Compatibility issues with new technologies

Why Maintenance is Ongoing

Software maintenance is continuous because:

  • User needs change over time
  • Technology evolves
  • Security vulnerabilities emerge
  • Operating systems and hardware are updated
(b) Discuss the impact of software maintenance on the long-term sustainability of a system. How do maintenance activities contribute to the security, performance, and usability of software over time?

Software maintenance ensures long-term sustainability by keeping software functional, secure, and efficient.

Security

  • Fixes vulnerabilities and security flaws
  • Applies security patches
  • Protects systems from cyber threats

Performance

  • Optimizes code and database queries
  • Improves system response time
  • Reduces memory and CPU usage

Usability

  • Updates the user interface
  • Fixes user experience issues
  • Adds features based on user feedback

Overall Impact

Maintenance increases system lifespan, reduces system failures, and ensures the software remains relevant to changing business and technological environments.

(c) Given that maintenance often involves working with legacy systems, what strategies can software engineers use to efficiently manage and update older software without introducing new issues?

Strategies include:

  1. Refactoring: Improve code structure without changing functionality. It makes legacy code easier to maintain.
  2. Comprehensive Testing: Use automated tests to verify system stability. It prevents new bugs during updates
  3. Documentation Improvement: Update missing or outdated documentation. It helps developers understand the system
  4. Modular Updates: Modify small components instead of the whole system. It reduces risk of system-wide failures
  5. Version Control Systems: Track changes and enable rollback if issues occur

Question 02​

(a) Explain the role of Change Management and Configuration Management in software maintenance. How do these components help maintain software quality and stability?

Change Management

Change management controls how modifications are requested, evaluated, approved, and implemented.

Roles:

  • Tracks change requests
  • Evaluates impact before implementation
  • Ensures proper approval before changes

Benefits:

  • Prevents unauthorized modifications
  • Reduces system disruption
  • Maintains software reliability

Configuration Management

Configuration management manages software components, versions, and system settings.

Roles:

  • Maintains version control
  • Tracks system configurations
  • Ensures consistency across environments

Benefits:

  • Avoids version conflicts
  • Helps developers revert to stable versions
  • Ensures system stability during updates

Together, these processes ensure that software changes are controlled, documented, and safely implemented.

(b) Why is Testing and Quality Assurance essential in the maintenance phase? Describe the types of testing involved in software maintenance and their importance.

Testing ensures that updates or fixes do not break existing functionality.

Importance of Testing in Maintenance

  • Detects new bugs introduced during updates
  • Ensures system reliability
  • Maintains software quality

Types of Testing

  1. Regression Testing: Ensures existing features still work after modifications.
  2. Unit Testing: Tests individual components or functions.
  3. Integration Testing: Ensures updated modules work with other components.
  4. System Testing: Verifies the whole system functions correctly.
  5. Acceptance Testing: Confirms the system meets user requirements after updates.

These tests ensure the system remains stable and reliable after maintenance activities.

(c) Discuss the significance of Performance Monitoring and Optimization in maintaining software efficiency. What tools or techniques can be used to ensure software performance remains optimal over time?

Performance monitoring helps identify system bottlenecks and inefficiencies.

Benefits:

  • Prevents slow system response
  • Detects resource overuse
  • Improves scalability and reliability

Techniques

  • Code optimization
  • Database query optimization
  • Load balancing
  • Caching frequently used data

Common tools used for performance monitoring include:

  • Application Performance Monitoring (APM) tools
  • Log analysis tools
  • System monitoring dashboards
  • Automated alert systems

These tools help detect performance issues early and maintain efficient software operation.

Question: 03​

(a) Discuss different types of software change and give reasons why changes occur.

Types of Software Changes

  1. Corrective Maintenance: Fixes bugs and errors found after deployment.
  2. Adaptive Maintenance: Adjusts software to new environments such as new hardware or operating systems.
  3. Perfective Maintenance: Improves performance or adds new features.
  4. Preventive Maintenance: Improves system maintainability to prevent future problems.

Reasons Changes Occur

  • Discovery of bugs
  • Changing user requirements
  • Security updates
  • Technology upgrades
  • Regulatory or business changes

Artificial Intelligence and Machine Learning analyze system data to predict future failures.

Examples:

  • Detect abnormal system behavior
  • Predict software failures
  • Recommend maintenance actions

Benefits

  • Early detection of issues
  • Reduced downtime
  • Improved system reliability
  • Better resource planning

Challenges

  • High implementation cost

(c) Why is software documentation considered a critical component of maintenance? What are the challenges in maintaining up-to-date documentation, and how can organizations ensure its effectiveness?

Software documentation helps developers understand system design, features, and functionality.

Benefits:

  • Easier debugging and updates
  • Faster onboarding of new developers
  • Clear understanding of system architecture

Challenges

  • Documentation becomes outdated quickly
  • Developers may neglect documentation updates
  • Lack of standard documentation practices

Ensuring Effective Documentation

  1. Continuous Documentation Updates: Update documentation during every code change.
  2. Documentation Standards: Use consistent templates and formats.
  3. Automated Documentation Tools: Generate documentation from code comments.
  4. Documentation Reviews: Include documentation checks during code reviews.

This ensures that documentation remains accurate and useful for long-term maintenance.

Question 04​

(a) Explain why it is important to reuse software instead of writing it from scratch.

Software reuse is the practice of using existing software components, libraries, frameworks, or code in new software projects instead of developing everything from the beginning.

Importance of Software Reuse

  1. Reduces Development Time

    • Existing components are already implemented and tested.
    • Developers spend less time coding and more time integrating features.
    • Projects can be completed much faster.

    Example: Using an existing authentication library instead of creating a login system from scratch.

  2. Lowers Development Cost

    • Less coding means fewer developer hours.
    • Reduces testing and maintenance costs.
    • Organizations save money by avoiding duplicate work.

  3. Improves Software Quality

    • Reused components have often been tested in many applications.
    • Bugs are already identified and fixed.
    • The resulting software is generally more reliable.

  4. Increases Productivity

    • Developers can focus on solving new problems instead of recreating existing solutions.

    For example:

    • Instead of writing a database engine,
    • developers use MySQL or PostgreSQL.

  5. Reduces Risk

    • Since reused software has already been deployed successfully, the risk of unexpected failures is lower.

  6. Promotes Standardization

    • Using common libraries and frameworks ensures consistent coding practices and easier maintenance.

  7. Easier Maintenance

    • Widely used reusable components receive regular updates, bug fixes, and security patches.

  8. Encourages Knowledge Sharing

    • Reusable software promotes collaboration across teams because developers can share common components.
4(b)(i). What is the first step that you would take?

The first step is to perform a Reuse Assessment and Planning.

This includes:

Step 1: Analyze Existing Software Assets

Identify:

  • Source code
  • Libraries
  • APIs
  • Documentation
  • Design patterns
  • Test cases
  • Frameworks

Determine which assets can be reused.

Step 2: Identify Business Goals

Understand why the company wants software reuse.

Possible goals:

  • Reduce development cost
  • Faster product delivery
  • Improve software quality
  • Standardize development

Step 3: Assess Current Development Process

Study:

  • Development workflow
  • Version control
  • Build systems
  • Documentation quality
  • Coding standards

Step 4: Select Reusable Components

Classify components according to:

  • High reuse potential
  • Moderate reuse potential
  • Not reusable

Step 5: Create a Reuse Repository

Build a centralized repository where reusable assets can be stored, documented, and searched.

Step 6: Define Reuse Policies

Establish:

  • Coding standards
  • Documentation requirements
  • Versioning rules
  • Approval process

Result

A structured reuse program with reusable assets, clear policies, and a repository.

Question 05​

(a). How do different software maintenance process models handle the balance between quick bug fixes and long-term maintainability, and what are the trade-offs associated with each approach?

Software maintenance models differ in how they prioritize immediate bug resolution versus long-term software quality and maintainability. The major models are compared below.

Maintenance ModelHandling Quick Bug FixesHandling Long-Term MaintainabilityTrade-offs
Quick-Fix ModelApplies immediate patches to solve problems quickly.Little attention is given to software design or documentation.Advantage: Fast and low-cost initially. Disadvantage: Code quality degrades over time, making future maintenance difficult.
Iterative Enhancement ModelBug fixes are implemented in planned iterations after analysis.Each iteration includes refactoring, documentation, and testing, improving maintainability.Advantage: Better software quality and easier future maintenance. Disadvantage: Bug fixes may take longer than emergency patches.
Reengineering ModelDoes not focus on immediate bug fixes.Improves the overall architecture by restructuring or redesigning the software.Advantage: Extends software life and reduces technical debt. Disadvantage: Expensive, time-consuming, and may interrupt development.
Boehm's Maintenance ModelPrioritizes bug fixes based on risk and business impact.High-risk issues and architectural improvements are addressed systematically.Advantage: Efficient resource allocation and reduced maintenance risk. Disadvantage: Requires detailed risk analysis and careful planning.

Conclusion

  • Quick-Fix Model emphasizes speed but sacrifices maintainability.
  • Iterative Enhancement Model balances bug fixing with continuous improvement.
  • Reengineering Model prioritizes long-term maintainability over immediate fixes.
  • Boehm's Maintenance Model uses risk assessment to balance urgent fixes and long-term software quality.
(b). What role does risk assessment play in Boehm's Maintenance Model, and how does it compare to other models in terms of prioritizing maintenance tasks?

Role of Risk Assessment in Boehm's Maintenance Model

Risk assessment is the core feature of Boehm's Maintenance Model. Before performing maintenance, each requested change is evaluated according to its potential risks.

The model considers factors such as:

  • Technical complexity
  • Impact on system stability
  • Business importance
  • Cost of implementation
  • Probability of failure
  • Security implications
  • User impact

Based on these factors, maintenance tasks are prioritized.

Example

Suppose a company receives three maintenance requests:

  • Fix a security vulnerability.
  • Correct a spelling mistake in the user interface.
  • Add a new reporting feature.

Using risk assessment:

  1. Security vulnerability → Highest priority.
  2. Reporting feature → Medium priority.
  3. UI spelling correction → Lowest priority.

This ensures that critical issues are addressed before minor improvements.

Comparison with Other Models

ModelMethod of Prioritizing Tasks
Quick-Fix ModelPrioritizes the most urgent problems with little analysis.
Iterative Enhancement ModelPrioritizes tasks according to the development iteration or release plan.
Reengineering ModelPrioritizes architectural improvements and code restructuring.
Boehm's Maintenance ModelPrioritizes tasks based on risk, cost, impact, and business value.

Advantages of Boehm's Model

  • Reduces maintenance risk.
  • Focuses resources on high-impact issues.
  • Improves software reliability.
  • Supports informed decision-making.
  • Balances short-term fixes with long-term quality.
(c). In what scenarios would an organization choose the Reengineering Model over the Iterative Enhancement Model, and what factors should be considered when making this decision?

Scenarios for Choosing the Reengineering Model

An organization should choose the Reengineering Model when the existing software has significant structural or architectural problems that cannot be effectively resolved through small, incremental improvements.

Typical scenarios include:

  1. Legacy Systems
    • Older software may use outdated technologies, making maintenance increasingly difficult.
    • Example: A banking application written in COBOL that needs modernization.
  2. Poor Software Architecture
    • If the system has become difficult to understand due to years of quick fixes and modifications, restructuring is necessary.
  3. High Maintenance Cost
    • When maintaining the existing software costs more than improving its architecture, reengineering becomes more economical.
  4. Technology Migration
    • Organizations may need to migrate from obsolete platforms to modern technologies, requiring major restructuring.
  5. Performance and Scalability Issues
    • If the software cannot meet current performance or scalability requirements, reengineering may be required to redesign the system.
  6. Security Improvements
    • Systems with outdated architectures may contain vulnerabilities that are difficult to address through incremental enhancements.

Factors to Consider Before Choosing Reengineering

Technical Factors

  • Quality of the existing code
  • Software architecture
  • Technology obsolescence
  • Complexity of the system

Economic Factors

  • Cost of reengineering
  • Expected maintenance savings
  • Return on investment (ROI)

Business Factors

  • Business criticality
  • Project deadlines
  • Customer requirements
  • Availability of resources

Organizational Factors

  • Availability of skilled developers
  • Management support
  • Risk tolerance
  • Training requirements

Comparison: Reengineering vs. Iterative Enhancement

Suitable ForLegacy systems, outdated technology, poor designStable systems requiring continuous improvements
CostHigh initial investmentLower incremental cost
TimeLonger implementationShorter development cycles

Question 06​

(a). Explain the role of program understanding in maintenance activities.

Program understanding is the process of analyzing and comprehending the structure, functionality, logic, and behavior of an existing software system before making any modifications. It helps maintenance engineers understand how the software works so they can make changes safely and effectively.

Role of Program Understanding in Maintenance

  1. Understanding Existing Code

Before modifying software, developers must understand:

  • The purpose of the program.
  • How different modules interact.
  • Data flow and control flow.
  • Relationships among classes, functions, and files.

This reduces the likelihood of introducing new errors.

2. Identifying Bugs​

Program understanding helps developers:

  • Trace the source of errors.
  • Identify faulty modules.
  • Understand the root cause instead of only fixing symptoms.

Example: If an online banking application calculates incorrect interest, understanding the calculation module helps locate the exact defect.

3. Supporting Software Modification​

When adding new features or changing existing ones, developers need to understand:

  • Which modules will be affected.
  • Dependencies between components.
  • Possible side effects of the changes.

4. Improving Software Quality​

Understanding the code allows developers to:

  • Remove redundant code.
  • Simplify complex logic.
  • Improve readability and maintainability.

5. Assisting Reengineering and Refactoring​

Before restructuring legacy software, engineers must understand:

  • Existing architecture.
  • Design decisions.
  • Business rules embedded in the code.

6. Reducing Maintenance Cost​

Well-understood software requires:

  • Less debugging time.
  • Faster implementation of changes.
  • Fewer maintenance errors.

Importance in Different Maintenance Types​

Maintenance TypeRole of Program Understanding
CorrectiveLocate and fix defects accurately.
AdaptiveUnderstand the impact of environmental changes.
PerfectiveSafely implement new features and enhancements.
PreventiveIdentify areas needing refactoring to prevent future issues.

Conclusion​

Program understanding is a fundamental maintenance activity because it enables developers to analyze existing code, identify defects, implement changes safely, improve software quality, reduce maintenance costs, and support successful corrective, adaptive, perfective, and preventive maintenance.

6(b). Discuss the comprehension process models and their application to maintenance tasks. (3 Marks)

Definition​

A program comprehension process model describes how software engineers understand an existing software system during maintenance. These models guide developers in analyzing code, documentation, and system behavior before making changes.

The three main comprehension models are:

1. Bottom-Up Model​

Description​

Developers begin by studying small program elements and gradually build an understanding of the entire system.

Steps:

  • Examine statements.
  • Understand functions.
  • Analyze modules.
  • Understand the complete architecture.

Application​

Useful when:

  • Documentation is unavailable.
  • Maintaining legacy software.
  • Debugging unknown code.

Advantages​

  • Provides a detailed understanding.
  • Effective for unfamiliar systems.

Disadvantages​

  • Time-consuming.
  • Difficult for very large systems.

2. Top-Down Model​

Description​

Developers first understand the overall system and then examine detailed components.

Steps:

  • Study system requirements.
  • Understand software architecture.
  • Analyze modules.
  • Examine source code.

Application​

Useful for:

  • Feature enhancement.
  • Software design modification.
  • Systems with good documentation.

Advantages​

  • Faster overall understanding.
  • Easier planning of modifications.

Disadvantages​

  • Depends heavily on accurate documentation.

3. Opportunistic (Hybrid) Model​

Description​

This model combines both Top-Down and Bottom-Up approaches. Developers switch between high-level design and low-level code as needed.

Application​

Commonly used in real software maintenance because engineers often alternate between architecture diagrams and source code while solving problems.

Advantages​

  • Flexible.
  • Efficient.
  • Suitable for large software systems.

Disadvantages​

  • Requires experienced developers.
  • Can become complex if not managed carefully.

Applications to Maintenance Tasks​

Maintenance TaskSuitable Comprehension ModelReason
Bug fixingBottom-UpFocuses on detailed code analysis to locate defects.
Adding new featuresTop-DownStarts with understanding the system architecture before modifying components.
Large legacy system maintenanceOpportunisticCombines architectural understanding with detailed code inspection.
RefactoringOpportunisticRequires both high-level design knowledge and low-level implementation details.

Conclusion​

Program comprehension models help maintenance engineers understand existing software before making changes. Bottom-Up is effective for debugging, Top-Down is useful for feature enhancement and design modifications, while the Opportunistic Model is the most widely used in practice because it combines both approaches for efficient maintenance.

6(c). What is the most important difference between generic software product development and custom software development? What might this mean in practice for users of generic software products? (4 Marks)

Difference Between Generic Software Product Development and Custom Software Development​

1. Generic Software Product Development​

Generic software is developed for a large market of users rather than a single customer.

Characteristics:

  • Designed for many organizations or individuals.
  • Requirements are determined by the software company based on market research.
  • Sold commercially to multiple customers.
  • One product serves many users.

Examples:

  • Microsoft Office
  • Adobe Photoshop
  • Google Chrome
  • VLC Media Player

2. Custom Software Development​

Custom software is developed for a specific customer or organization according to their unique requirements.

Characteristics:

  • Requirements are provided directly by the client.
  • Built for one organization.
  • Highly tailored to business processes.
  • Usually not sold to other customers.

Examples:

  • Hospital Management System
  • University Student Information System
  • Banking Core Software
  • Airline Reservation System

Most Important Difference​

The key difference is who defines the requirements.

  • Generic Software: Requirements are decided by the software developer based on the needs of a broad market.
  • Custom Software: Requirements are specified by a particular client and tailored to their specific needs.

Comparison Table​

AspectGeneric SoftwareCustom Software
Target UsersMany usersOne customer or organization
RequirementsDefined by the developer based on market demandDefined by the client
CostLower per user because development cost is sharedHigher because it is built specifically for one client
CustomizationLimitedExtensive
Development TimeUsually shorter for end users (already available)Longer because it is developed from scratch
ExamplesMicrosoft Office, PhotoshopHospital, banking, or university systems

What This Means for Users of Generic Software Products​

Advantages​

  • Lower purchase cost because costs are shared among many users.
  • Immediate availability without waiting for development.
  • Regular updates, bug fixes, and security patches.
  • Well-tested and reliable due to widespread use.
  • Extensive documentation and community support.

Disadvantages​

  • Limited customization to individual needs.
  • Users may need to adapt their workflows to fit the software.
  • Features that are not useful to all users may still be included.
  • Dependence on the vendor for updates and future improvements.

(a) Challenges in Modernizing a 30-Year-Old Legacy System

Updating a three-decade-old inventory system while keeping it operational (often called "changing the engines while the plane is flying") presents several critical challenges:

  • Legacy Knowledge Gap: After 30 years, the original developers are likely gone. Documentation may be missing or outdated, making it difficult to understand the business logic embedded in the old code.
  • Data Integrity and Migration: Moving 30 years of data to a modern architecture is risky. Ensuring that data remains consistent and uncorrupted during the transition is a major hurdle.
  • Zero-Downtime Requirement: Since the system must remain operational across multiple warehouses, you cannot simply "turn it off" to upgrade. This requires a phased approach (like the Strangler Fig pattern) which increases architectural complexity.
  • Integration with Modern Tech: The old system may use obsolete protocols or flat-file databases that do not easily communicate with modern APIs or cloud environments.
  • Resistance to Change: Staff accustomed to the 30-year-old interface may resist the new system, requiring significant training and change management.

(c) Why Making the Product Open Source Could Be Beneficial

In the scenario described, open-sourcing the specialized product offers several strategic advantages:

  • Co-Development with Customers: Since the new customer wants involvement in the configuration, open-sourcing allows them (and their developers) to contribute code directly. This reduces the workload on the small company while meeting specific requirements.
  • Scalability: Doubling the customer base can overwhelm a "small company." An open-source model allows the community to help identify bugs and provide support, making the software more robust as it grows.
  • Standardization: If the product becomes an open-source standard in its niche, it becomes harder for competitors to displace it. The company can then pivot its business model toward consulting and high-end support rather than just selling licenses.
  • Trust and Transparency: New, large customers may feel more secure knowing they have access to the source code, ensuring they aren't "locked in" if the small provider goes out of business.
